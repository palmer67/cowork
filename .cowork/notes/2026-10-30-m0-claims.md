## 一条实测推翻的设计假设（已改文档）

架构书 §3.2 原本用「owner 进程还活着」判断 claim 是否有效。e2e 直接推翻：

```
A 车道 claim src/auth/login.ts      → exit 0
B 车道 claim src/auth/login.ts      → exit 0  ← 本应 exit 2
  已清理失效占位 src/auth/login.ts（pid 19432 已退出）
```

根因：每次 `cowork claim` 都是独立进程，命令一退出 pid 就死，下一条命令把它当残留清掉。
占位形同虚设，而这恰好是本工具唯一要防的事。

改为只由 `createdAt + ttlMs` 判定（默认 24h，`COWORK_CLAIM_TTL_HOURS` 覆盖），
pid 降级为展示与审计。已写入 DECISIONS D7 与 AGENTS.md「占位的存活语义」。

## 已验证的边界

| 场景 | 结果 |
|---|---|
| 两条车道占同一条相对路径 | exit 2 |
| 文件落在对方目录前缀内 | exit 2 |
| 名字前缀相同但路径段不同（`src/auth` vs `src/authx`） | 放行 |
| 多路径中一条冲突 | 整单失败，不落半份 |
| 同一工作树、不同 `COWORK_AGENT_ID` | 互斥 |
| 占位进程已退出但未过期 | 仍然占着 |
| 过期 | 下一条命令顺手回收 |
